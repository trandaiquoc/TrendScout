1. About this demonstration

TrendScout is a local demonstration for reviewing keyword candidates alongside source evidence. It does not require an account, Google sign-in, or Google OAuth. The application is designed to run on the operator's computer; these policy pages alone do not host or operate the application.

Features and providers are selected by the operator. A Fetch sends only the bounded, server-curated queries required by the selected source. The current YouTube feature is disabled until the owner approves and publishes this policy and explicitly enables the feature. This acceptance run has made no live YouTube API request.

2. YouTube API Services

If the owner later enables YouTube, a user-triggered Fetch may request public video search results from YouTube Data API Services. The application can receive video IDs and watch URLs, titles, descriptions, channel IDs and names, publication times, thumbnails, broadcast status, result position, query scope, and collection timestamps. It does not request view counts or other video statistics for this feature.

TrendScout uses this information to show attributed source evidence and Fetch status. It does not currently use YouTube records for keyword extraction, trend scoring, or product recommendations. A US region filter describes video availability or relevance; it does not prove that creators or viewers are in the United States.

The API key is resolved by the local server and is not sent to the browser. TrendScout does not access a user's Google account or private YouTube data. Before a YouTube Fetch can proceed, the application must be configured as approved and the user must accept the exact current TrendScout policy version. Until the documents are approved and published, the server blocks that feature.

Use of YouTube API Services is subject to the YouTube Developer Policies, the YouTube Terms of Service, and the Google Privacy Policy.

3. Other sources and third parties

When configured and selected, the local demonstration can contact the relevant source provider. Current integrations include Wikimedia's public API, Google Trends RSS, and Google or Bing web search through SerpApi; YouTube is separately gated. Providers receive the source query and request parameters needed to answer it. The current query plans are curated by the server and do not include a free-text search box for personal information.

The operator's local installation may also retrieve model files for its local CPU-based text processing when those files are not already available. TrendScout's configured processing does not send collection text to a hosted generative-AI service. Hosting, model-download, DNS, network, and provider telemetry outside TrendScout have not been independently audited for this draft.

TrendScout does not sell source records or use them for advertising. The local application does not synchronize its SQLite databases to a TrendScout cloud service. Provider processing remains subject to each provider's terms and privacy notice.

4. Browser and user data

The application has no user account or user profile. In the browser it stores display preferences (theme, language, selected Fetch defaults, and sidebar state) and, after the policy is published, the accepted policy version. It does not store YouTube API keys in browser storage. These values use browser local storage; clearing site data removes them. The current interface does not configure analytics cookies.

While the application is open, selected source results are held in memory for display. The local browser makes requests to the local TrendScout backend. A person's identity, browser history, or location is not collected by the YouTube source adapter.

5. Storage and Fetch history

On the Windows demonstration setup, the local SQLite files are stored under the current Windows user's profile: Collections and Fetch summaries under %LOCALAPPDATA%\TrendScout\collections-v1; source cache, Fetch checkpoints, quota reservations, and source refresh state under %USERPROFILE%\.local\state\trendscout\normal-google-live-v1. Exact paths can differ when the operator configures another local directory.

YouTube video records are kept in the YouTube-scoped source cache and Fetch checkpoint while needed to serve a result. The application is configured for an eight-hour cache freshness window, at most seven days of cache retention, and up to one hour for a completed Fetch receipt/checkpoint. An hourly local cleanup and cleanup at startup remove expired YouTube cache and checkpoint data. A request-time expiry check also prevents expired checkpoints from being returned.

The Collections database does not store YouTube videos as keywords or scoring observations. It can store a source manifest and counts for a Fetch. A targeted deletion removes YouTube manifest entries and adjusts mixed-source counts while preserving other source entries. Fetch IDs, status, quota reservations, refresh eligibility, and non-content operational records may remain as needed to prevent repeat requests and preserve operational history.

6. Logs, backups, and diagnostics

The application does not configure a file log for YouTube records. Standard server access and error output may be written to the console by the local process launcher; an operator or hosting environment may separately retain redirected output. The gateway is designed to keep API keys, request URLs, and provider response bodies out of its sanitized diagnostics. Console capture and retention are not controlled by TrendScout.

No automatic backup job for these local databases was found in the repository. Operators may make their own backups or copies; locations outside the known TrendScout data directories are not discoverable by the application. Backups must be checked and handled separately after a deletion request. No YouTube API records were found in the 19 SQLite backups inspected for this local acceptance review.

7. Deletion requests

There is no account-based self-service deletion feature. A request can be sent to the operator using the contact address that will be published after owner review. The operator must verify the requester through an independently known contact channel, stop the local application, preview the affected YouTube-only records, and run the documented local deletion command.

The implemented workflow removes YouTube cache entries, YouTube Fetch checkpoints and unshared checkpoint blobs, and YouTube-only Fetch summaries. It preserves Google, Bing, and Wikimedia records, shared quota ledgers, and source refresh schedules. The local deletion receipt retains an opaque request hash, timestamps, and counts, but contains no video IDs or requester contact details. The retention period for those receipts remains an owner decision in this draft.

The operator must separately review manual backups and any redirected console output. A user must clear browser site data on their own device to remove the saved policy version and display preferences. TrendScout's local deletion cannot remove information held by YouTube or another provider.

8. Policy changes and approval

Before publishing a change, the operator will update this page and its effective date, review the matching Terms of Service, and change the in-app policy version so users must accept the new version. The owner must confirm the operator identity and contact, storage and log practices, backup procedure, deletion-receipt retention, and any provider-specific terms before publication.
