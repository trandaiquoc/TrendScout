# D5 demo-first architecture — production gates remain open

**Status (12/11/2026):** local four-source synthetic demo verified; `DEMO_ACCEPTANCE=100%`. `PRODUCTION_MULTI_HOST_ACCEPTANCE=BLOCKED`, `D5_PRODUCTION_READINESS=PARTIAL`, and live provider activation is disabled. Current development/cloud accounts are personal; do not use personal Firebase/Firestore or credentials as production infrastructure. The D6/D7 roadmap separates company-owned onboarding/live activation from the local demo.

The anonymous browser reads capabilities and submits a server-controlled Fetch. The backend gates admission; durable coordination, quotas and bounded workers eventually call source-specific adapters, normalize observations, run discovery and publish versioned evidence to the dashboard. Public clients cannot control provider endpoints, plans, credentials, quota or authorization. Vercel remains read-only. Legacy `POST /api/runs` retains its Bearer requirement.

Provider credentials enter adapters through the backend `CredentialProvider` port. Account ownership, provider secret, runtime service identity, organization admin and anonymous public user are separate concepts. Secrets, connection status and non-sensitive configuration have separate boundaries. The D6 admin system will require independent authentication and authorization; no public dashboard login is introduced.

## D5 guarded query-source gateway (offline tested, not activated)

`LivePageGateway` has a separate controlled network constructor for the fixed SerpApi and YouTube hosts and a MockTransport-only constructor whose outputs are always `SYNTHETIC`. It validates a registered server-owned plan, scoped cursor, fixed source and approval metadata; a `GuardedAttemptRunner` reserves and rechecks the fenced attempt before outbound work. `GuardedQueryCollector` runs bounded queries/pages/retries, retains per-query evidence, reports incomplete retrieval and never combines SERP position with YouTube or Wikimedia metrics. A separate `WikimediaTopPageGateway` uses only the server-selected date and fixed top-per-country endpoint, requires operator contact in User-Agent, checks approval and reserves each bounded attempt. `D5SourceHandlers` joins these offline fixture paths to the fenced worker and optional synthetic-only cache. `DistributedPublicFetch` is exposed through an explicitly injected local/test synthetic API composition. This is not a production worker/deployment; live remains disabled and the original offline adapter constructors still reject live transport.

The local/test composition can use `LocalSQLiteAtomicStateStore` as a real file-backed `AtomicStateStore`. It enforces synthetic mode, owner-only database file permissions, bounded JSON records, and SQLite transaction locking across independent processes on the same host. Offline integration verifies API admission→worker→four fixture adapters→cache→readback, and eight worker processes competing on one queued Fetch. It deliberately rejects production/live profiles and `:memory:` databases. `DistributedWorkerRunner` provides a separately invocable bounded polling loop and graceful stop; the opt-in Firestore harness now has quota-race and crash-once/lease-recovery probes with a systemd runbook, but neither the manager lifecycle nor a two-host run has been verified. SQLite on a local filesystem is not a shared multi-host database; the local API demo still schedules one worker attempt as an ASGI background task. A shared production backing store remains unverified, so public live remains disabled.

`DistributedFetchWorker` now persists bounded source checkpoints and typed page/normalized-result receipts through `SourceCheckpointJournal`; crash-recovery tests cover Google, Bing, YouTube and Wikimedia after receipt commit, resuming without a duplicate outbound request. The unavoidable gap before the receipt becomes durable remains charged/fail-closed. Retry-After beyond the inline wait cap remains deferred; a real deployment still needs to prove durable scheduling, shared backing and recovery under actual host/process failure. Local tests do not establish production recovery.

The SerpApi search endpoint requires its credential as a query parameter; the gateway injects it beneath the outer HTTPX request logger so that logger sees only the fixed URL. The gateway also rejects credentials echoed in returned items, bounds response size and time, rejects redirects, suppresses upstream exception text and never returns raw provider responses. MockTransport tests check HTTPX log output; they do **not** prove that process-wide instrumentation, proxies, lower-level tracing, network observability or crash dumps cannot capture an inner URL. Such telemetry and egress controls, provider account/terms, trusted approval state, clock and distributed safeguards require independent review before D6 activation. In-flight requests cannot be recalled atomically when a switch changes, and expiry of a local slot cannot fence a paused process at an external provider. Public live remains disabled.

Provider documentation reviewed 2026-11-12: [SerpApi Google](https://serpapi.com/search-api), [SerpApi Bing](https://serpapi.com/bing-search-api), [SerpApi key placement guidance](https://serpapi.com/blog/fix-serpapi-errors-guide/), [YouTube search.list](https://developers.google.com/youtube/data/reference/rest/v3/search/list), and [Google API key header guidance](https://docs.cloud.google.com/docs/authentication/api-keys-use). Documentation is not evidence of credentials, access, quota, cost or live connectivity for this project.

Business logic uses `AnalysisStorage` for the legacy analysis path and `AtomicStateStore` for D5 admission, jobs, quotas, cache and source checkpoints; concrete Firestore SDK use stays behind its adapter. The Firestore adapter is not wired into the public application and its tests use fakes only: neither Firestore nor its emulator has been contacted. Local demo composition uses `LocalSQLiteAtomicStateStore`, which is single-host and synthetic-only. This verifies the storage boundary, not Firestore transaction semantics, production IAM, TTL/deletion, backup deletion or distributed behavior. [Admission design](D5_QUOTA_CACHE_QUEUE_AND_ADMISSION_DESIGN.md), [discovery design](D5_KEYWORD_EXTRACTION_AND_TREND_DETECTION.md), [approval register](D5_FOUR_SOURCE_LIVE_APPROVAL_REGISTER.md) and [D6 plan](D6_PROVIDER_ACCOUNT_CREDENTIAL_AND_LIVE_ACTIVATION_PLAN.md) describe remaining work and decisions.

Separate `DEMO_ACCEPTANCE` and `PRODUCTION_MULTI_HOST_ACCEPTANCE` gates, with their current status, are maintained in the [D5 blueprint](D5_FOUR_SOURCE_LIVE_INTEGRATION_BLUEPRINT.md). ## Architecture decision records (D5 scope)

These records describe the current demo implementation and an unapproved production direction. They do not authorize using personal cloud resources or selecting a permanent company platform.

### ADR-D5-01 — Storage boundary and demo backing

- **Status:** Accepted for the local synthetic demo; production backing not selected.
- **Decision:** Keep business logic on `AnalysisStorage` / `AtomicStateStore` ports. Use file-backed SQLite only for local/test synthetic demo execution. Keep the existing Firestore adapter behind the port as a candidate; do not connect it to the public app or use the owner's personal project.
- **Alternatives:** In-memory state is not durable enough for Fetch; directly binding business logic to Firestore violates the storage boundary; a new managed SQL service would add provisioning, cost and migration work without organization approval.
- **Consequences and open evidence:** Demo needs no Firebase account. Production requires an organization-owned non-production store, IAM review, transaction/contention/size/cost testing, TTL and backup deletion policy, and two-host recovery evidence. No migration or resource provisioning is included in D5.

### ADR-D5-02 — Queue and worker boundary

- **Status:** Implemented for offline/local tests; production execution topology remains unapproved.
- **Decision:** Represent local Fetch jobs, leases, fencing and quota reservations through `PublicAdmission` on the atomic storage port. Exercise workers through the bounded `DistributedWorkerRunner`; the local API demo may execute one bounded attempt as an ASGI background task. Do not enable that local composition as Vercel or production background processing.
- **Alternatives:** Process-local queues lose work and quota state on restart; a separate managed queue plus database adds a second service and cross-service atomicity/reconciliation; Vercel request/background execution has not been approved or shown to provide the required durable worker lifecycle.
- **Consequences and open evidence:** Offline tests cover independent processes on one SQLite host and the harness prepares a real shared-store/two-host probe. Production still needs an approved supervisor, shared backing and queue-delivery design, plus real crash recovery and quota-race evidence. The minimal option must be reconsidered against resources the company actually provides; this ADR does not choose a paid service.
